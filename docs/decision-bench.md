# mst-ja-decision-bench

選択肢・はい／いいえ・スコアだけを返す decision model が、日本語のタスクをどれだけ正しく判定できるかを測るベンチマークである。
日本語で使う decision model を選ぶ人が、正しさと費用と速度を並べて比べられる。

結果は https://masseater.dev/decision-bench/ で公開している。

- 正解ラベルは、JNLI を除いて Claude Opus 5.5 だけで付けた
- スコアは Opus 5.5 のラベルとの一致率で、本当の正しさではない
- 勉強目的の実験なので、結果を過信しないでほしい

## タスク

| タスク         | 種類   | 件数 | 正解     | 出典とライセンス                                                   |
| -------------- | ------ | ---: | -------- | ------------------------------------------------------------------ |
| JNLI 含意関係  | Choice | 2434 | 人       | JGLUE JNLI v1.3 の valid（yahoojapan/JGLUE@6f071c0）、CC BY-SA 4.0 |
| 業務ルール判定 | Noul   |  500 | Opus 5.5 | Opus 5.5 で生成した架空の社内規程と事例、CC BY-SA 4.0              |

JNLI は人が付けた正解で採点する。
Opus 5.5 のラベルは JNLI の 200 件にも付け、人の正解との一致率を LLM ラベルの誤り率の目安として示す。

業務ルール判定は、架空の会社の規程と、それに適合するか問う事例でできている。
事例は 1 か所だけを変えて答えを逆にした 2 件で対を作っている。どの事例も、2 つ以上の条を組み合わせないと判断できない。

Opus 5.5 にラベルを付けさせた問題では、1 問を 3 回独立に聞く。
3 回の答えが割れた問題は `hard` として、表の数字とは別に数える。
業務ルール判定では、作るときに意図した答えと 3 回の多数決が食い違う問題も `hard` にする。

## 採点

採点は [Jev Decision Index](https://huggingface.co/spaces/multimodalart/jev-decision-index) のルールに合わせた。

- 問題文は全モデルで同じにし、モデルごとに調整しない
- 棄権・エラー・未対応の形式は不正解として数える
- raw は、Choice では macro-F1、Noul では 0.5 を閾値にした balanced accuracy である
- skill は `(raw - chance) / (1 - chance)` を 0〜1 に収めた値で、chance はランダムに答えたときの raw である
- 指数は各タスクの skill の平均で、性質の違うタスクをまたぐ参考値である
- 業務ルール判定では、対の両方に正解した割合も対の正解率として示す

Noul しか受け付けないモデル（span-01 系）には、Choice の問題を選択肢ごとの Noul に分けて聞き、「はい」の確率が最も高い選択肢を答えとする。
この聞き方は既存のベンチに例がないので、結果ではこの方法で答えたモデルに「*」を付ける。

答えられた問題の割合（coverage）、p50・p95 のレイテンシ、費用、確率の較正（ECE と Brier）は、正しさとは別の軸で示す。

ほかに次のベンチの採点と見せ方を取り入れた。

- [S1MB](https://github.com/hotchpotch/S1MB)。chance 補正した skill と、Noul の balanced accuracy
- [DecideBench](https://github.com/choyiny/decidebench)。1 か所だけ違う対と、対の正解率
- [JevBench](https://github.com/fstandhartinger/jevbench)。1,000 判定あたりの費用、p50・p95 レイテンシ、ECE と Brier
- [Arize の比較](https://arize.com/blog/decision-model-benchmark/)。二値の balanced accuracy と、較正誤差を別に示すこと
- [AIMultiple AIM-Decision](https://aimultiple.com/system-one)。費用と速度を指数に入れず別の軸で示すこと

## 手元で測り直す

前提として、Vite+ の `vp` と OpenRouter の API キーが要る。
問題と正解ラベル、これまでのモデルの応答はリポジトリに入っているので、測り直しに Opus 5.5 は要らない。

```sh
vp install
cd tools/bench
OPENROUTER_API_KEY=<キー> vp run bench
```

保存済みの応答は呼び直さないので、新しいモデルを足したときだけ OpenRouter に問い合わせる。
終わると `vp run bench` は、この README の結果の表と、サイトが読む `libs/bench-summary/summary.json` を書き換える。

問題とラベルを作り直すときは、Claude Code の `claude` コマンドと、JGLUE を clone したディレクトリが要る。

```sh
cd tools/bench
JNLI_VALID_JSON=<JGLUE を clone した場所>/datasets/jnli-v1.3/valid-v1.3.json vp run build:jnli
vp run build:rules
```
